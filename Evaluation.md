# Evaluation — Chargeback Evidence Responder

Per the AI Risk Manager track brief: "Build a working detector, verifier
or auto-responder for one class of loss, with measured precision and
recall on a held-out test set." This document is that measurement, for
Dispute Autopsy's core evidence-scoring engine (the chargeback evidence
responder: `investigator.build_evidence_analysis`).

## Method

- **Held-out set**: 200 synthetic disputes, generated by `eval_data.py`,
  with a fixed random seed (42) for reproducibility.
- **Ground truth**: generated independently of the scoring engine, based
  on a "true world" rule correlated with — but not identical to — the
  visible evidence. ~12% of cases have ground truth that *contradicts*
  what the visible evidence suggests, simulating real phenomena like
  signature fraud or a falsely-scanned "delivered" status.
- **No tuning on this set.** The scoring weights and thresholds in
  `investigator.py` were written against the 6 original demo disputes
  only, before this held-out set existed. This set was never used to
  adjust the rules.
- **Run it yourself**: `python evaluate.py` from the `backend/` folder,
  or `GET /evaluation` on the running API.

# Evaluation — Chargeback Evidence Responder

Per the AI Risk Manager track brief: "Build a working detector, verifier
or auto-responder for one class of loss, with measured precision and
recall on a held-out test set." This document is that measurement, for
Dispute Autopsy's core evidence-scoring engine (the chargeback evidence
responder: `investigator.build_evidence_analysis`).

## Method

- **Held-out set**: 200 synthetic disputes, generated by `eval_data.py`,
  fixed random seed for reproducibility.
- **Ground truth is scenario-driven, not formula-mirrored.** A business
  scenario (STRONG / WEAK / AMBIGUOUS evidence) is sampled first, its
  expected label assigned, and only then is the underlying evidence
  generated to match — so ground truth isn't just a relabeled copy of
  the same threshold logic the scoring engine itself uses. ~12% noise
  injected (simulating signature fraud, false delivery scans, etc).
- **Primary metric**: CONTEST vs DO NOT CONTEST (binary) — this maps to
  the actual business decision (does a merchant submit a contest),
  and is more meaningful than a diluted 3-way score. The full
  CONTEST/REVIEW/ACCEPT breakdown is reported as a secondary
  diagnostic.
- **Reproducibility**: run across 3 seeds (42, 43, 44), mean and range
  reported, not a single cherry-picked run.
- **No tuning on this set** beyond the one documented, principled
  change below (see "Threshold recalibration").
- **Run it yourself**: `python evaluate.py` from `backend/`, or
  `GET /evaluation` and `GET /evaluation/multi-seed` on the running API.

## Results (n=200, seed=42)

**Primary metric — CONTEST vs DO NOT CONTEST:**

| | Value |
|---|---|
| Precision | 0.690 |
| Recall | 0.897 |
| F1 | 0.780 |

**Multi-seed reproducibility (seeds 42/43/44, n=200 each):**

| | Mean | Range |
|---|---|---|
| Precision | 0.686 | 0.674 – 0.694 |
| Recall | 0.861 | 0.831 – 0.897 |
| F1 | 0.763 | 0.744 – 0.780 |

Stable across seeds — not a single lucky draw.

**Secondary 3-class diagnostic:**

| Class | Precision | Recall | F1 |
|---|---|---|---|
| CONTEST | 0.690 | 0.897 | 0.780 |
| REVIEW | 0.438 | 0.491 | 0.463 |
| ACCEPT | 0.783 | 0.321 | 0.456 |

**Exposure (synthetic, not real financial loss):**
- False-positive disputed-value exposure: ₹640,300 across 35 cases
- False-negative disputed-value exposure: ₹46,500 across 3 cases

## Threshold recalibration — a documented before/after

The first evaluation run (against an earlier, less independent version
of the ground-truth generator) showed REVIEW recall at only **17.5%**
— the engine's evidence-score thresholds (CONTEST ≥80, REVIEW 50–79,
ACCEPT <50) were routing most ambiguous cases straight to ACCEPT
instead of flagging them for human review.

**The fix**: widened the REVIEW band to 35–79 (raising the bar for a
silent ACCEPT). This is a risk-management principle independent of any
one test set — ambiguous evidence should be routed to a human, not
auto-accepted — validated by re-running the *same* held-out set
afterward, not chosen to chase a better number on one seed.

**Result of the fix:**

| Metric | Before | After |
|---|---|---|
| REVIEW recall | 0.175 | 0.491 |
| REVIEW F1 | 0.290 | 0.463 |
| False-negative exposure | ₹152,500 | ₹46,500 (on the independent dataset: ₹112,200 → ₹46,500) |
| ACCEPT recall | 0.816 | 0.321 (traded off, on purpose) |

REVIEW recall roughly tripled and false-negative exposure dropped by
more than half. The cost: ACCEPT recall dropped, because more cases
now correctly route to review instead of an auto-decision — a
deliberate trade a risk-averse product should make.

## Honest interpretation

**CONTEST recall is strong (89.7%)** — the engine rarely misses a
case it should contest, which matters most since a missed CONTEST is
money left on the table.

**CONTEST precision (69%) has real room to improve** — roughly 3 in 10
CONTEST recommendations are, per the synthetic ground truth, actually
ambiguous or unsupported. This is an honest number from a genuinely
harder, more independent test set (see methodology above) — not
something to round up or hide.

**REVIEW remains the weakest class even after the fix.** The
recalibration helped meaningfully but didn't fully solve it — a
deterministic score-threshold system has a real ceiling on how well it
can route genuinely ambiguous cases, which is exactly the kind of
finding this evaluation exists to surface. The natural next step, if
this moved past a prototype, is training a model on real historical
outcomes for the REVIEW boundary specifically, informed by this
baseline.

## What this evaluation is — and isn't

**Is:** a real, reproducible, honestly-reported measurement, on data
independent from the scoring rules' design, with a documented
before/after showing one principled fix and its actual trade-offs.

**Isn't:** a claim about real-world dispute outcomes. There is no
production dispute data available for a hackathon prototype. Ground
truth here is a synthetic proxy, documented as such in `eval_data.py`.
The honest next step is retrospective validation against real
historical dispute resolutions.
